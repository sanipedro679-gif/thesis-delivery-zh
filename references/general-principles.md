# 可跨项目复用的规则

这些规则描述工作中容易失效的机制。具体章节、术语、数量和格式由当前项目传入。

| 共性机制 | 执行规则 | 项目参数与例外 | 验证方式 |
| --- | --- | --- | --- |
| 要求缺少来源或适用范围 | 每项要求记录来源、文稿类型、章节与生效条件；修改后同步受影响位置 | 学校模板、教师意见、用户补充；冲突需要明确处理依据 | 更换项目后，旧要求不自动生效；同项目各位置保持一致 |
| 材料来源与可用用途混淆 | 为材料分别记录允许用途、采用位置和排除理由 | 有的材料只供结构或格式参考；用户指定也不自动成为有效证据 | 合法用途正常，越权引用或无解释遗漏提示处理 |
| 获取资料与证明论点混淆 | 分开记录书目核对、资料取得、实际阅读及逐处论点支持 | 摘要可支持其明确表述的概括；精确事实依相应原始来源 | 已下载或已阅读但缺少论点映射时仍待核验 |
| 同一信息的多个表示失去同步 | 为来源与要求保留稳定标识，变更时同步正文、目录、文献表和台账 | 引用制、章节结构及编号起点由项目确定 | 修改顺序后重引仍一致；不同编号规则各自符合配置 |
| 标题与段落功能不匹配 | 审核每节实际承担的论述功能及前后衔接 | 文稿类型决定组织方式；允许学校要求的合并小节 | 人工核对标题与原文；结构脚本只核对可识别项目 |
| 提出措施却缺乏依据与评价 | 连接事实、问题、原因、措施、执行条件与评价 | 证据与篇幅决定论述深度；计划与已完成结果分别表达 | 每项主张能追溯证据或明确假设，不虚构实施结果 |
| 写作过程信息进入提交稿 | 按句子功能区分实际论述、必要限制和内部操作说明 | 有解释价值的限制保留；工具披露依学校规定 | 人工复核其用途，不靠固定短语一律删除 |
| 局部格式检查替代整体检查 | 分开核对段落、样式继承、字符、表格、分节与页面 | 字体、字号、间距、缩进等均为项目参数；必要留白保留 | 改变参数仍正确判断；结构检查和页面查看分别记录 |
| 检查对象与交付版本不一致 | 在实际成品上检查，用哈希绑定输入、报告和页面 | 修改内容或格式后，只重做受影响的必要检查 | 旧版本结果不能证明新成品合格 |
| 从单次纠正直接生成普遍禁令 | 先定位根因，再写触发条件、参数与例外，以不同参数和正常对照验证 | 项目要求留在项目；尚未证明的推广保持候选 | 新进程能重载有效规则，误伤正常情况的更新不能生效 |

新反馈先归入已有机制；能用现有机制解释就完善原规则，避免积累同义提醒。无法排除项目特有原因时，暂留项目记录，等待更多证据。
